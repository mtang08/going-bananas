2. New services/routes are developed beside existing ones. New calendar endpoints can be registered, but active-data migration and replacement navigation remain disabled until integration cutover. Avoid duplicate `/checkins` handlers: prepare new router and mount it only when old router is adapted atomically.
3. Add an explicit integration-owned cutover task after TASK-012/013/014 and replacement UI/coaching adapters pass. Service `migrate_legacy_state(session, *, dry_run: bool) -> MigrationReport` runs in one transaction under the same advisory lock used by agent writes, plus `app_state` row lock. It creates a unique durable migration marker/mapping; repeated execution is a no-op. No writes race across authority changes. App-state `planning_authority` switches `legacy`→`calendar` only after validation; all old mutation routes must then delegate or return explicit upgrade-required errors, never continue writing an invisible second plan.
4. Preserve every legacy row and revision byte-for-byte. Create one imported calendar baseline from the exact currently active membership, keeping each original planned-session UUID as `session_uid`; retain historical plans/revisions in archive APIs. Carry completion links, including linked historical sessions outside current membership, with source IDs and timestamps. Do not infer completed-as-planned from existence of a link: retain link and use unknown/not-assessable until comparison succeeds. Add `legacy_import` calendar kind and immutable legacy mapping/source payload fields.
5. Convert explicit duration minutes→seconds/distance km→metres; preserve full original target as `legacy_payload`, including locked state. Imported runs use a distinct `legacy_unstructured` marker exempt from structured-custom validation; never invent recipes, repeat structures or intensity anchors from prose. Imported unknown kinds must be reported, not discarded. Legacy check-ins retain IDs/timestamps/versions/raw payloads; categorical feeling/symptoms must not become fabricated numerical fatigue/severity. Expose archived records with `schema_version:1`; only verified equivalent fields map to v2. This requires an explicit legacy DTO alongside new v2 DTOs.
6. Preserve old audit/history read routes through MVP. Archive rollback must not mutate legacy tables after cutover; UI exposes it as historical provenance, while new rollback uses calendar versions. Export/restore must include both generations and mapping/marker state. Acceptance uses populated synthetic 0009 fixtures with cross-plan membership, completed links, edited check-ins, agent history and recurring strength; assert exact row/payload retention, active-state parity, replay, failed-cutover rollback, and preserved exports. Downgrade must refuse once new data exists; reversal is tested restore, not destructive migration.
