# Go backend rewrite specification

**Decision.** Go is the long-term backend for Going Bananas. The first implementation milestone is a working proposal list in Home, served by Go from a synthetic PostgreSQL database. At cutover, Go owns every application write for the normal training week, coaching review, imports and recovery procedures. The rewrite is complete when those paths also run without a Python backend or temporary SDK adapter.

The HTTP inventory was verified against published `main` at `de3bdf5`, including the iPhone check-in flow, typed proposal list, native dashboard coach and macOS login preference. The readiness rehearsal used `fc6490c`. Its fixtures cover the first read-only slice. [Implementation readiness report](go-rewrite-readiness.md) · [Current architecture](architecture.md)

## What crosses the language boundary

Keep the React app, PostgreSQL, the offline phone queue, the running knowledge base, and the coach's manual proposal-acceptance workflow. Preserve the athlete's existing database and private files in place. API shapes and internal schemas may evolve when a slice updates every consumer and gives a reason for the change. Saved records, outstanding drafts, queued phone entries, retry receipts, and supported backups each have consumers that can outlive the old executable.

## Target design

- **One Go module and one executable with subcommands.** Start in `backend-go/` alongside the Python implementation. The local HTTP server, worker and CLI share application commands and queries. They can run as separate processes as they do today. Keep the phone listener separately bound and narrowly routed, including if it later becomes a subcommand. The research content and Codex coaching skill stay outside the application binary.
- **One contract per migrated HTTP operation.** Check in an OpenAPI document for the migrated routes. Start from the actual proposal-list schema and its documented 422. Generate strict Go handler interfaces and wire types using `oapi-codegen` with `net/http`, and React types using the existing `openapi-typescript`. Switch the generation source in the same change that moves the route. Most existing FastAPI responses are bare dictionaries. Reconstruct those contracts from handlers, real consumers and synthetic examples as their turn comes. Use the verified OpenAPI 3.1 schema directly. Pin the generators and check required, nullable and literal values at the wire boundary. Map request-validation failures to the existing error envelope. Check generated output for drift and run Go build/test/vet and the frontend typecheck in the normal project checks. [Current generator](../scripts/api-types.py) · [Go generator and validation support](https://github.com/oapi-codegen/oapi-codegen/blob/v2.9.0/README.md) · [TypeScript generator](https://openapi-ts.dev/cli)
- **Typed SQL and explicit transactions.** Use `pgx/v5` with `sqlc` for named PostgreSQL queries. Feed the generator a schema derived from a migrated synthetic database and verify it against migrations. Pass transaction-bound queries to code that writes. Keep raw provider payloads and historical JSON documents at their boundaries. Decode fields used in decisions into named Go types. Model civil dates separately from instants, distinguish omitted/null/value on patches, and preserve an explicit zero on observations. Validate enums, ranges, field presence and relationships at the boundary. A compilable Go struct can still contain an invalid zero value. [sqlc with pgx](https://docs.sqlc.dev/en/stable/guides/using-go-and-pgx.html) · [Existing phone observation tests](https://github.com/mtang08/going-bananas/blob/69c78b39f180ee62563e5a956c77891731b192a7/backend/tests/integration/test_phone_checkins.py)
- **Organize by behavior.** Planning owns calendar versions and proposal decisions. Training owns observations, matching, metrics and feedback. Ingestion owns jobs, provenance and reconciliation. Coaching reads these through typed queries and owns the filtered snapshot. Start packages when the first slice needs them. Keep wire types at the transport boundary and put a rule shared by CLI, worker and HTTP in one application function. Reuse PostgreSQL locks and the durable job tables.

### Go lint and build checks

`make check` includes `make check-go`. The project pins Go 1.27.4 and golangci-lint v2.15.0. From `backend-go/`, the target runs the following commands and fails on a diagnostic. With the pinned release, `run` checks formatting as well as the enabled analyzers. [Project lint configuration](../.golangci.yml) · [Pinned linter release](https://github.com/golangci/golangci-lint/releases/tag/v2.15.0) · [golangci-lint configuration](https://golangci-lint.run/docs/configuration/file/)

```sh
go build ./...
golangci-lint run --config ../.golangci.yml ./...
go test -race ./...
```

| Enabled check | Reason to keep it |
| --- | --- |
| `govet` and `staticcheck` | Catch suspicious calls, including mismatched formatting arguments, lost context cancellation and invalid uses of standard APIs. The lint run includes vet analysis. |
| `errcheck` and `errorlint` | Surface ignored errors and error comparisons that lose meaning after wrapping. These matter when a transaction fails or a provider error must become a retry. |
| `ineffassign` and `unused` | Flag overwritten assignments and unused private declarations as Python paths are replaced. |
| `bodyclose` | Flag HTTP responses whose bodies the caller leaves open, including in Garmin and Google adapters. |
| `gofmt` | Keep handwritten Go in canonical format. Apply formatting locally and check it without rewriting files during verification. |

Build and test generated OpenAPI and sqlc packages. Regenerate them and fail on drift. Fix generated findings at their schema, query or generator. Apply source-level suppressions narrowly and explain why the finding is safe. For handwritten pgx queries, check row closure on early return and iteration errors in review and database tests. In a pgx v5.7.6 probe, `sqlclosecheck` passed a query that abandoned rows after the first result. [Linter catalog](https://golangci-lint.run/docs/linters/)

Exercise worker cancellation and competing dashboard turns under the race detector as those slices land. Run `govulncheck ./...` (v1.10.0) separately in CI or before a release. It consults the Go vulnerability database and reports known affected code the application calls. An ordinary local edit can still run its build, lint and tests offline with cached tools and modules. [Go race detector](https://go.dev/doc/articles/race_detector) · [Go vulnerability management](https://go.dev/doc/security/vuln/)

## Data handoff and rollback

1. **Establish the schema boundary.** At implementation time read the actual Alembic head, compare the database with the expected schema and stop on mismatch. Preserve existing keys, sequences, partial indexes, checks, revision chains, stored JSON and frozen history tables. Keep historical Alembic upgrades runnable offline for older supported backups. Introduce forward SQL migrations from a verified baseline. Exercise both a fresh install and an upgrade of a historical synthetic database. Compare the catalogs, including foreign keys, column defaults and partial-index predicates, verify required singleton rows, then compare history reads, receipts and raw-file checksums. [Migration head](../backend/app/migrations_head.py) · [Schema upgrade tests](../backend/tests/integration/test_schema_upgrade.py)
2. **Rehearse on disposable targets.** Restore an existing-format test backup into a new database and private directory. Run the normal Go entry points, including demo UI, helper, phone retry, worker and backup/restore. Compare observable results and durable side effects against the reference. Check sequences by making subsequent inserts. Exercise a lost worker, a retry and a failed restore. The source must remain recoverable. [Backup and restore](../backend/app/services/backup.py) · [Restore verifier](../scripts/verify-restore.py)
3. **Switch the single real writer.** Once the owner schedules the switch, stop new writes from the API, phone forwarding, worker, standalone sync, launchd and coach CLI. Let in-flight commands finish or reconcile their durable state. Take and verify a final private backup of PostgreSQL and its allowlisted files. Run a read-only preflight against that mode, database and private root with startup refresh and the worker disabled. Check the schema, latest accepted calendar, active draft, weekly summary, sync checkpoints and raw references. Backups exclude credentials, so check local provider configuration and permissions separately. Then start the normal supervisor, including its startup refresh and worker, and resume launchd and phone delivery under the same origin. Preserve backup retention. [Startup supervisor](../scripts/serve.py)
4. **Recover without losing new observations.** Up to the first migration, startup refresh, background or user write, the previous release can resume against the untouched schema. After new writes, return to the old binary only if the rollback rehearsal proved it can read and safely continue from that state. Otherwise stop writers, retain the post-switch state and receipts, and repair forward or reconcile them into a separately restored target. A pre-switch backup alone cannot recover observations accepted afterward.
