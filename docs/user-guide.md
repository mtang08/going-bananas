Going Bananas is your local training journal and accepted running plan. Open [Home](#home) to find today’s workout, record what happened, and see what needs a decision. Bring ordinary planning questions to the Codex coach on Sunday. Use the app to review and apply any changes you agree to.

## Start here

### Your normal rhythm

On an ordinary day, check Today, train and record, then respond if there is a useful observation or a prompt. A recording that imported and matched on its own needs no confirmation. Leave an uneventful day there and save planning chat for your review.

- **Optional morning check-in** → If you have set up the private iPhone app, record first-step ankle pain there, even on a rest day. This is separate from delayed feedback linked to a run.

- **Before training** → [Home](#home) → **Today’s plan**. Read the accepted purpose, dose, effort and adjustment cues. Open the workout in [Calendar](#calendar) if you need its full structure. If a material change affects what you can do, report it before treating the plan as settled.
- **During training** → Record the run on Garmin and the lift in Strong. Follow the accepted prescription on your watch or from Calendar. **Download week** gives you text for reference, and you can set up a Garmin workout separately if you want watch prompts. Check off rehab separately in Calendar.
- **After training** → If a match looks unclear, check it in Calendar. Open the recording if you want to compare execution, add effort the watch missed, or record a relevant delayed response. Log completion manually only when you know you completed the workout.
- **Sunday evening** → Check **Planned vs done** and **Needs attention** on Home, then start the Sunday review in Codex. Discuss the changes before asking the coach to save a draft. Finish on the proposal page by accepting the changes you want.
- **When something changes midweek** → Follow the matching workflow below. Leave the accepted calendar as it is until you edit it directly or accept a coach proposal.

The app imports records, matches activities and evaluates evidence using local rules. The coach in Codex interprets the evidence, answers questions, and drafts changes when you ask. Garmin and Strong remain your recording tools. Google Calendar supplies travel context through a read-only connection.

### Open the right workspace

On the Mac running the app, open [Going Bananas](http://127.0.0.1:8000). The header shows **Real data**, **Demo data**, or **Test data**. Use Real for personal training. Demo and Test use separate databases and private directories. Start another mode from the terminal only after stopping the existing app on that port. Follow [README.md → Run on this Mac](../README.md#run-on-this-mac) and [docs/operations.md](operations.md) for setup and startup. See **Maintain the local workspace** below if the app is unavailable.

### Set up a new calendar

In [Settings](#settings), open **Set up your plan**. Confirm the first run day of your every-other-day cycle, check the strength routine and confirm the actual strength/mobility schedule, and verify the timezone. The setup pattern is one quality workout, one long run, and easy running on the other run days in the week. Choose **Create my 14-day calendar**. This creates the initial schedule. For coached workouts and an accepted block objective, start a block review separately.

Enter your goals and races if you have them. Check which dates Garmin and Strong cover before drawing conclusions from the first import. Record any confirmed running restrictions before asking for a prescription. If setup reports a failure, refresh Settings and inspect which profile, routine, and calendar parts saved before retrying.

### Where to go when something happens

- **I have today’s workout and can do it** → [Home](#home) → **Today’s plan**. Follow the accepted prescription and record the workout at its source.
- **Something affects today’s run** → Use **Record check-in** in the top bar for symptoms or material context. Use [Home](#home) → **Needs attention** or ask Codex for an exception review if the plan needs adapting.
- **The recording is absent, delayed, or on the wrong day** → [Settings](#settings) → **Sync** to check imports, then [Calendar](#calendar) → **Record outcome** or **Mark complete** as appropriate.
- **I need to record effort or delayed response** → From [Home](#home) or [Calendar](#calendar), open the run. Supply only the observations you know.
- **I need to move, remove, or shorten an upcoming workout** → [Calendar](#calendar) for a direct edit if you already know what you want. Ask the coach if you want the tradeoff assessed.
- **I have a temporary break or a clinician’s instruction** → Use [Home](#home) for a running interruption or [Settings](#settings) → **Running limits** for a confirmed restriction. These record different facts and can coexist.
- **I have travel, a new goal, or a race** → Record it in [Settings](#settings), then tell the coach when it materially changes the plan. Use the race prompt on Home when a post-race review is due.
- **It’s my regular review, or my block needs a decision** → Start with “Sunday review” in Codex. The coach routes it to a rolling plan or a block review.
- **I have a new calibration result or want to choose a quality workout** → Describe the new evidence or the quality slot to the coach. Review the targeted proposal in the app.
- **I have a proposal or want to change my mind** → [Home](#home) → **Needs attention** → **Review**. Revise the open draft in chat, select the changes you want, reject, or discard. For an already accepted change, use Calendar’s **Plan versions** if a restore is available.

### Example week

On Monday, open an accepted easy run on Home, run it with Garmin, and check the linked recording after sync. If watch effort came through, review it and add an app value only if you want to correct it. On Tuesday, complete your scheduled rehab independently. When the delayed feedback window opens, record what you noticed after Monday’s run.

On Thursday, a schedule conflict means the weekend long run needs a different day. If you want the coach to weigh the tradeoff, tell it what changed and which days are available. It can compare the move with nearby demanding sessions. When the draft looks right, open it from Home, inspect **Two-week schedule impact**, and accept the changes you want. Check the resulting day in Calendar.

On Sunday, open **Planned vs done**. Compare the agreed change with the actual run and your response. If there is still no recording or response, say what you know and leave the rest unknown. Ask Codex for your Sunday review, agree on any changes in chat, and finish the decision in the app.

> Use $going-bananas-coach for my Sunday review in real mode. Review my current block. The long run moved to Saturday, and I recorded my response in the app. Talk through what to keep or change and what to check next.

## Daily check-in

Use **Record check-in** in the top bar to report fatigue, pain, gait change, illness, or relevant context. Use the recorded run for effort and delayed feedback linked to that workout. Enter symptom location, side, severity, and timing as known. The app records your observation and may display a finding or review recommendation. The finding explains when to review. A check-in leaves the accepted plan intact.

Open [Home](#home) for **Today’s plan**. An upcoming run links to its calendar workout, and a linked recording opens the run with its feedback. Use Calendar for the full prescription, including warm-up, intervals, recovery, targets, the coach’s brief, and your notes. If Home shows a restriction or an interruption on today’s run, review the conflict before treating the displayed plan as a workout to carry out.

Use [Settings](#settings) → **Sync** if a recording is missing. Open the Activity page to enter effort or a delayed response when useful. A timestamped response belongs to the run you open. See **Sync, imports and workout feedback** for the exact controls.

New observations and recorded outcomes can lead to findings. Repeated or converging signals may raise a finding on Home. A new symptom, illness, or gait change can warrant earlier attention. See **Exception review**.

### Restrictions, strength and rehab

In **Settings → Running limits**, enter the original instruction, its source and first day. You can pause running, exclude quality sessions, or set maximum distance or duration per run. Enter a confirmed last day when you know it. A reassessment date keeps an open-ended limit in force until you update it. Current conflicts can appear on Today and in Calendar, and new plans and edits are checked against the dates and dose. The app records constraints and symptoms for planning. Seek appropriate help for concerning symptoms or uncertainty about clearance.

Record lifting in Strong and confirm the actual **Strength routine** and **Strength schedule (weekly or alternating)** in Settings. For an alternating schedule, use a Week A Monday reference. Record required and optional mobility distinctly. Updating these settings informs future planning. Change an already accepted dated lift in Calendar or through a proposal. Missing Strong coverage leaves lifting unknown.

Use **Add session → Rehab** in Calendar or ask the coach to schedule it in your draft. Enter a duration, mark each slot complete independently, and keep the total within 15 minutes per day. Rehab can share a day with a run or lift and counts separately in the weekly digest. If a clinician gives you a routine, use that routine as your prescription for the rehab slot.

## Return after a running interruption

With **Record a running interruption** under **Today’s plan**, use the following flow. If that action is absent and no interruption panel is showing after Home finishes loading, your running copy may predate this feature. Tell the coach which dates you are unavailable or when you will reassess, and review any proposed changes in the app.

On [Home](#home), under **Today’s plan**, choose **Record a running interruption**. Pick a reason and the first day you are unavailable. For a known break, enter your **First day available**. If your return is uncertain, choose **My return date is open** and set **Reassess on**. Reassessment keeps the break in place until you confirm availability or end the interruption.

Saving or editing the interruption leaves your accepted workouts and recorded outcomes intact. Today flags a planned run on a day covered by the interruption. Calendar edits and proposal decisions check for new, moved-in, or increased runs on unavailable dates. Review the existing sessions with the coach and decide which to remove or move out of the window. Home lists affected runs to leave behind or discuss, so you can resume without trying to make up every missed workout. Once you confirm a return date, **First run to review** can point to an existing, easy aerobic session that fits known limits and travel availability. If there is no suitable session, Home explains what to review. Use your recorded running limits separately from the first day you have time to run.

Open **Discuss with the coach** on Home to ask for a return plan. When you review a draft, **Running break in this proposal** shows what the checked changes would do to upcoming affected workouts. Selecting or clearing a change updates that preview. Only an accepted decision applies the selected changes to Calendar.

After your first run back is recorded, Home links to its feedback. Review how the run went and record effort or delayed response where appropriate. Use **End interruption** to clear the break when you are ready. Your feedback and accepted calendar are preserved.

## Sunday review

Start one manual coaching review on Sunday evening. The coach chooses the scope.

> Use $going-bananas-coach for my Sunday review in real mode. Review my current block and talk through the plan with me. My schedule changes and feedback are: …

The coach checks the active block and its review date. With no block, it helps establish one. When the block is due or an early-review trigger applies, it reviews the objective and response. Otherwise, it reviews the rest of the current block, from today through the block's review date and always at least 14 days ahead, keeping day 8 onward provisional.

In **Planned vs done**, the follow-up on an accepted run shows the original dose, the reason for the change, the recorded outcome and effort, any delayed response, and the plan's next check. It flags later calendar edits. Use the links to reopen the decision or the recording.

While reviewing a pending proposal, **Two-week schedule impact** recalculates when you change the checked rows. It shows changes in planned running time and distance and the dates of affected sessions. For a moved run, look for nearby demanding work before deciding whether to accept. **Block → Goal progress** brings the latest reported benchmark, the block indicators, and the next scheduled check together.

Start a fresh Codex conversation for a new review. If there is already a draft for this decision, continue in its conversation or ask a fresh chat to open the existing draft. A question such as “Does this workout serve my goal?” can end with an answer and no draft.

You start each review yourself. **Weekly review day** in Settings records your preferred day. It creates no schedule or automatic proposals. Review earlier when a material change, symptoms, or a new goal changes the decision.

## Exception review

The Sunday review is the normal control loop. Between Sundays, the app checks check-ins, post-run RPE against each session's intent, completions, and races. An isolated HRV, resting-HR, sleep, or pace reading can stay logged for Sunday. New symptoms, illness, or gait changes can warrant earlier attention.

- **Logged** findings appear under **Logged for Sunday review** on Home.
- **Caution** or **Hold** findings appear under **Needs attention** with an exception review recommendation.
- **Needs bigger review** calls for a block review. When a symptom or illness needs outside evaluation, deal with that first.

When Home recommends an exception review, copy its prompt. If a weekly or block draft is still open, decide or discard it before opening a separate exception draft.

> Use $going-bananas-coach for an exception review. Read the open findings in the app and patch only what they require.

The coach scopes an exception to the affected sessions within the next seven days. Days 8 onward stay outside the patch. The proposal lists the sessions it leaves unchanged, a reassess date, what to watch for, when to return to plan, and when to escalate. Accepted changes show **Patched · reassess** with the day on Home and in Calendar.

On the reassess day, Home shows **Reassess due**. Choose **Mark resolved** when you are back to normal, or **Still not right** to keep it for the coach. To ask the coach to reassess:

> Use $going-bananas-coach to reassess the open exception patch.

When a finding needs a bigger review:

> Use $going-bananas-coach for a block review. An exception needs a bigger review.

Use **Dismiss** on a finding that is wrong or already handled. Review, resolving a patch, or dismissal can close a finding. Keep an open finding in view even when a metric improves.

## After a race

When a recently completed PR or benchmark race qualifies for review, Home offers a prompt for the race. A training run at an event gets no race review. Use the first 1–3 days to observe recovery and tell the coach what actually happened. Copy the prompt from Home, which names the race, or use this prompt.

> Use $going-bananas-coach for a post-race review of … on ….

The review records pacing, effort and the limiting factor, conditions, symptoms, and recovery. It may propose new intensity anchors and changes inside the committed week. A race that is the block's ending benchmark is reviewed in the block review instead.

## Block-ending benchmark

A block includes a benchmark when there is no credible prior result, that result is roughly six weeks old by the benchmark window, or a race in the block calls for a race or benchmark effort. The benchmark falls in the week before the block’s last week. The block proposal specifies its protocol, date, and what counts as progress or consolidation. A time trial appears with a **Benchmark** badge.

Within seven days of the block’s review date, the regular review routes to a block review. The result can support progressing, consolidating, rescheduling the test, or planning the next block. Check sync if you ran the test and the result is missing.

A block without a benchmark is judged on the review criteria shown on [Training block](#block), such as workout progression, aerobic efficiency on easy runs, completed key sessions, and effort against intent. A block review without a benchmark keeps its intensity anchors. Credible test or race evidence can support a separate calibration decision.

The app matches the benchmark run automatically. If it chose the wrong run, open [Training block](#block) and use **Choose activity** in the Block benchmark card. **Use automatic match** undoes your choice.

When the benchmark is complete, Home recommends a block review.

> Use $going-bananas-coach for a block review. Review the block benchmark.

That review compares the result with earlier benchmarks of the same protocol, decides whether to progress, consolidate, or only recalibrate, and can propose recalibration when the result is credible. Results stay in [Trends](#trends) under **Benchmark history**. A missed benchmark also leads to a block review. Bring up illness or symptoms before deciding whether to reschedule.

## Training blocks and weekly plans

A block gives the weekly plan an objective, start date, review date, progression focus, and observable review criteria. It also records qualities to maintain, constraints, and reasons to review early. A weekly plan chooses the sessions that serve that accepted objective from today through the block's review date, and always at least 14 days ahead.

Use this prompt to establish your first block.

> Use $going-bananas-coach to establish my first training block in real mode. Propose its objective, start and review dates, progression dimension, review criteria, and sessions through its review date using my current evidence and priorities.

The proposed block becomes active only after you select and accept its block change in the app. Creating or revising the draft does not activate it.

Open [Training block](#block) to inspect the current direction, review timing, and block benchmark. Use the timeline for elapsed time and **Goal progress** for the evidence behind the block’s assessment. A block review considers actual response and indicators before continuing, consolidating, or changing direction. A regular weekly review cannot silently change the block.

## Events and your goal race

Use **Settings → Goals** for a broader aim. Record its horizon and priority. Edit its status as it changes, including when you pause, finish, or drop it. Tell the coach when a goal change warrants revisiting the block.

Add races and events relevant to your training under [Settings](#settings), **Events**, with its date, distance, a purpose, and, if you want one, a goal time. The purpose guides preparation and execution.

- **Race it (PR attempt)** → you are racing for a result. The coach plans a taper sized to the event.
- **Benchmark effort** → a quality effort. The coach reduces the load around it only enough for an interpretable result, with no full taper.
- **Training run** → a session that happens to fall at an event. No taper, you do not run it maximally, and it gets no race review.

Your upcoming events are listed in priority order. Rank 1 is your **goal race**, marked with a badge. Use **Move up** and **Move down** on each row to reorder them. Every training block builds toward the goal race, so the [Training block](#block) page shows the earlier blocks, the current block, the emphases the coach expects between now and race day, your other events by date, and race day. The coach revisits the expected emphases at each block review. Home's block line names the goal race.

Rank decides what the blocks build toward. Purpose decides how each event is prepared for and run. A Race it 10K ranked third still gets its own taper inside the current block, and the coach says what that costs the goal-race build in its proposal. Accept the proposal, or change the event's purpose, to decide.

Your goal time expresses what you want to achieve. The coach judges whether it is plausible from your recent evidence and says how confident it is.

When the goal race changes (you reorder events, cancel it, or its date passes), the Training block page and Home say the block was planned for another race, and the next Sunday review is a block review. Nothing on the calendar changes until you accept a proposal. Events entered after a block was planned have the same effect once.

## Travel from Google Calendar

The app can read your Google Calendar and find trips from the flight events Gmail adds, so you do not have to tell the coach about travel. Connect from the terminal using [README.md → Google Calendar travel](../README.md#google-calendar-travel).

- **Sync calendar:** in [Settings](#settings), open **Travel and Google Calendar** and press **Sync calendar**. It reads 30 days back and 180 days ahead and says how many events changed and how many trips need review. The button appears only in real mode.
- **Detected trips:** a trip found from your flights starts as **Possible trip**. **Confirm** it, **Edit** it (**Save and confirm** also confirms it), or **Dismiss** it. Use **Show dismissed** and **Restore** if you want to bring a dismissed trip back.
- **When the calendar changes:** if a flight changes or disappears after you confirmed or edited a trip, the trip shows **Calendar changed**. Choose **Use calendar version** or **Keep mine**. A sync never overwrites your edits.
- **Add trip:** for travel without flights, or a vacation or other disruption at home, enter the dates, destination, and destination timezone.
- **Access and availability:** on any trip, set running access and gym access, and mark single days **Unavailable** or **Shorter or alternative**. Leave availability at **Unknown** when you are unsure. The coach keeps its plan conditional.
- **Calendar events:** under **Calendar events**, check each synced event's category. Choose **Automatic** to return to the app's category. Marking an event as a flight, or not, updates your trips.

Trip days show a badge on the [Calendar](#calendar): **Travel**, **Possible travel**, or **Travel changed**, followed by "unavailable", "shorter session", or "travel day" where they apply. Each badge links to Settings.

The coach sees each trip’s dates, destination timezone, flight times with their timezone source, access, availability, and confirmation status. It plans around unconfirmed trips conditionally and may ask you to verify the destination timezone before placing a session. It keeps your strength schedule and run rhythm through a trip and does not turn missed travel sessions into catch-up work. Changing a trip can make an open coach draft stale. App dates stay in your home timezone during trips. A morning run far from home can appear on the previous day even when the coach uses your destination dates for planning.

## Review and revise a proposal

Discuss the plan in one chat. Ask for a shorter workout or a different day and the coach will work from the same review context. When the plan looks right, say “looks good” or “publish it.” The coach saves the agreed plan and provides its review link. **Pending your review.** On Home, open **Needs attention → Review** to read the coach’s brief and inspect each proposed change, including workout details, block changes, and calibration anchors when present. The saved brief records the headline, reasoning, uncertainty, what would change the decision, and the next check. Open a change row for its reason, effort, focus, and when to adjust. **Sources** lists the research behind the advice by title. The full explanation stays in your chat with the coach. **Two-week schedule impact** reflects the checked changes and shows dated moves, known run dose changes, and nearby demanding work where identifiable. Some mixed-unit or unspecified doses remain unknown. Inspect changes outside the two-week period separately. Proposals and blocks saved before this format keep their old text under **Earlier format**.

- Valid session changes start checked. Uncheck any you want to reject, select any block or anchor changes separately, then choose **Accept selected**.
- A **Skip lift** row shows the date, the affected lift, and why the coach proposes skipping it. The decision applies only to that lift. Review other sessions on the same date separately.
- Review related calibration anchors with any targets that depend on them.
- For a saved no-change review, choose **Accept (no changes)** to record your acknowledgment. **Reject all** records that you declined every proposed change.
- Opening a proposal or receiving it in chat does not apply it.
- Exception reviews add an **Exception** card with the reason, plan impact, sessions left unchanged, reassessment, and what to watch for. Race reviews add a **Race review** card. Block benchmark reviews add a **Benchmark review** card. Settled patches appear under **Patch updates**.

To refine an open draft, continue the same conversation. Try a concrete counterproposal.

> Could we move the long run to Saturday?

Once you agree, the coach updates the same proposal ID and review link, with revision history. Review selections reset when a new revision arrives. A later check-in, import, travel edit, restriction or other relevant evidence may make a draft stale. Ask the coach to refresh its evidence and revise the same draft. If the app reports a revision conflict, use **Reload proposal** and check the latest selections. For an invalid draft, inspect the reported issue and ask the coach to revise or discard the draft. Stale and invalid drafts still count as the one open draft.

Use **Discard proposal** on the review page to abandon a draft without making an acceptance or rejection decision. It leaves the open list and its history stays available. Accepted, partially accepted, rejected, and discarded proposals are final. A later change needs a new proposal. The accepted Calendar shows which edits actually applied.

## Calendar edits, outcomes and restore

### Keep the plan and the recording separate

Open a session’s **Session details** to inspect the accepted prescription or edit your own notes. Use **Add session** on today or a future day. For an eligible existing session, use **Edit**, **Move**, or **Delete** and confirm. These are direct changes to the accepted calendar. The app keeps a new plan version and may mark a pending coach draft stale. Historical, completed, and locked sessions are protected. **Download week** creates a text file of the workouts for the displayed week.

A past run performed on a different day is an outcome to reconcile. Open **Record outcome** on the planned run, pick the recording from the planned or adjacent day, and choose **Link run**. Home can point you here when matching needs your input. A linked run keeps its actual recording date. Choose **Skipped** if you skipped the workout, or **Not recorded** if its outcome is unknown. If you know you finished without a recording, use **Mark complete**. **Undo manual completion** corrects that choice. Measured pace, time, distance, and reps stay unknown until there is a recording.

### Restore an eligible version

In Calendar, open **Plan versions** and use **View** to inspect a version and its changes. If the app offers **Restore**, confirm which version you intend to restore. Restore writes a new calendar version and keeps protected sessions intact. You can also explicitly ask the coach to undo an eligible calendar version. Inspect Calendar afterward. If a proposal is still pending, use its decision controls. It has made no edits to undo.

## Weekly mileage and the week view

Home's weekly mileage uses Monday–Sunday in your profile timezone. It adds recorded running distance so far to the remaining accepted runs. Time-based sessions use workout speed targets or median observed speed from the previous 28 days and show an estimate. Past unrecorded sessions are not added to the forecast, and pending drafts never affect it.

Missing data and incomplete plan coverage are labeled. Treat the projection as a planning aid, especially where distance is estimated. Use the Calendar arrows to move between weeks. Choose **This week** to return to the current week or **Session details** to read the full prescription, the coach’s brief, and your notes. Notes are yours alone: the coach writes the session brief and never edits your notes. Sessions marked provisional are an outlook that may change. Follow the badge on each saved session.

The weekly count includes **Completed · self-reported**, including a lift completed before its Strong export was imported. A later matching recording can fill measured details.

Reps are matched to your watch workout in order. Split laps within a step are combined. An unrecorded warm-up, recovery, or cool-down can be skipped. A skipped work rep counts as unrecorded. The comparison is unavailable when equally plausible matches give different counts of completed reps.

On treadmill runs, the overall planned-versus-done assessment omits pace targets and time-in-target. Confirmed manual treadmill paces can inform individual interval analysis. Known distance can contribute to the overall comparison when the plan has no planned duration.

## Occasional calibration and goal changes

A new race result, test, or sustained change in workout execution may justify revisiting intensity anchors. Missing saved anchors alone do not require a test or an easy-only reset. Tell the coach what evidence is new.

> Use $going-bananas-coach to review intensity calibration in real mode using my new test or race evidence: …

For a new goal, race, or substantial scheduling constraint, request the broader review explicitly.

> Use $going-bananas-coach to review this goal or race change in real mode: … Explain its block implications and the plan through the block's review date.

You can ask the coach to choose a workout for an existing quality slot. Give the date and what you want to work on. You can also ask how to interpret a run, compare options, or change a preference. Tell the coach if you only want advice.

To enter a known anchor yourself, use **Settings → Intensity anchors**. Choose its kind, measurement, method, confidence and effective date, then save. A new value of the same kind supersedes the prior one. Intensity metrics depend on anchors and usable sensor data. Enter an official race result in **Settings → Events** when you know it and ask for recalibration if the evidence merits it.

## Sync, imports and workout feedback

- **Garmin** → [Home](#home) or [Settings](#settings) → **Sync now** in Real mode. Let the queue finish and check which datasets succeeded, their newest observation, and any partial or failed statuses. A local macOS sync schedule, if installed, can do this while the web app is closed. Saved records remain available if Garmin access lapses.
- **Treadmill confirmation** → choose **Review treadmill run** when the sync card lists a dated run. Enter any known corrected lap pace in minutes and seconds per displayed unit. Blank laps keep Garmin’s values. Use **Confirm and import** when ready or **Review later** to leave it pending. Check Calendar after import.
- **Strong** → log lifting in Strong and export its CSV when you want current lifting evidence in Going Bananas. Use the preview and apply procedure in [README.md → Strong import](../README.md#strong-import). Existing lifting history remains readable between exports. An unresolved overlap stays ambiguous.
- **Effort and execution** → open the run from the linked session or the weekly list. **Session RPE** shows the Garmin value when available. **Enter RPE** or **Change RPE** records your own value, which takes precedence while retaining the Garmin value. Where offered, add a reason for a materially different execution. Timing, intervals, and other metrics use the available recording.
- **Delayed response** → open **Symptoms after this run** and use **Answer delayed check**, **Add late response**, or **Add delayed feedback** when offered. The window opens 16 hours after the recorded end. Use the run’s dated record even if you dismissed its reminder. Answering **No** explicitly records no reported pain. Leaving a question blank preserves uncertainty.

If an entry stays pending, reconnect Tailscale, wake the Mac, check that the API and phone gateway are running, and reopen the icon or choose **Retry sync**. The original entry keeps its date on retry.

The iPhone app records morning ankle observations. See [docs/iphone-checkins.md](iphone-checkins.md) for the daily phone workflow. Use the Mac for the calendar, other check-ins, imports, and coaching.

## Maintain the local workspace

Use [README.md → Fresh setup](../README.md#fresh-setup) for setup and [docs/operations.md](operations.md) for startup, mode isolation, automated sync, credentials, backups, restore, and the versioned coach skill. These are occasional owner tasks. Open the app directly whenever it is already serving your workspace. Start the local database when needed. Use the runbook before changing schema or modes, and leave migrations and testing out of ordinary training use.

- **The app or database is unavailable.** Verify the app is running on the Mac and check local database readiness. Use `make doctor` and the operations runbook if startup fails. Stopping with `Ctrl+C` stops the launcher’s app processes and keeps saved records. Close the running app before switching modes or starting a second copy on the same port.
- **A provider is unavailable or a sync is partial.** Keep using the accepted plan and saved feedback. Inspect the dataset status in Settings. Retry the failed sync after access recovers or a rate limit clears. Follow the owner documentation for Garmin credential renewal and Google reconnection. Keep secrets out of chat. If the model is unavailable, Calendar, local feedback, and direct edits still work while the local app and database are up.
- **A source is missing.** Check Garmin coverage, pending treadmill review, Strong export dates, or Google Calendar connection separately. Record an outcome from what you actually know. Preserve unknown observations when requesting a review.
- **You are updating or recovering the workspace.** Follow the real-mode backup and migration procedure in [docs/operations.md](operations.md). Restore to a separate database and private directory, verify before switching, and retain the original until you are satisfied. Keep backup archives private. Manage provider credentials and token files separately.
- **Coach access or protocol fails.** Work in the project checkout and refer to the repo-local skill. Follow the skill update instructions in [docs/operations.md](operations.md) if your installed copy is older or the app reports an incompatible protocol. Start a fresh Codex session after an update as needed. Use the accepted calendar while you resolve it.
