# Open decisions for the owner

These decisions do not block discovery. The suggested defaults keep the first iterations useful and reversible. Decide them when the corresponding slice is planned. The [backlog](../../backlog.md) retains the original requests and user choices.

| Decision and point of use | Working default | What would change it |
| --- | --- | --- |
| **When is feedback worth asking for?** Before iteration A | Reuse watch RPE. Retain the existing selective delayed prompts after long runs or recent symptoms. One explicit answer when it could change the next dose. Include “unknown/skip.” | Observe an eligible run to distinguish deliberate nonresponse, inaccessible device, mistimed prompt and unclear benefit. Expand capture only for a recurring unanswered question. |
| **What should a restriction mean in the app?** Before B | The athlete records the source and exact instruction. Represent only known affected exposures, limits and dates/review condition. Surface ambiguous wording before a potentially incompatible recommendation. | An actual constraint cannot be expressed or the athlete needs to distinguish a firm clinical limit from a coaching preference. Confirm any health-related change with its appropriate owner. A date can trigger reassessment without granting clearance. |
| **Who owns rehab content and what indicates progress?** Before E | Schedule a supplied routine, let the coach propose frequency under the 15-minute daily budget, and record completion separately. Keep formal progressions and criteria with the athlete or clinician who supplied them. | The athlete requests help selecting exercises or already has a meaningful functional benchmark. Determine who sets it, how it is measured and what decision it changes. Hip mobility merits its own slot/measure only if useful. |
| **Which commitment should define adherence?** Before C | Use the accepted prescription in force when the runner trained. Show a previous accepted commitment only for a material change or a question about plan churn. | The owner regularly wants to know how realistic Sunday's original plan was. Then retrieve that version too, preserving accepted changes and unknown outcomes in both comparisons. |
| **Which preferences should outlive a chat?** During C | Save only an athlete-confirmed statement that affects a recurring decision, with scope and a way to review/correct it. Start with existing typed fields. | A later conversation repeats the question or the feedback cannot fit existing fields without misleading future reviews. No need to import whole chat transcripts. |
| **What monthly cost and review time are acceptable?** Before D | Keep ordinary days local. Measure the current review on existing access and count marginal subscription cost separately from per-use fees. Use a cheaper/model-optional route only when acceptable judgment has been demonstrated. | Agree a dollar ceiling, tolerable Sunday time and what happens if the specified model is unavailable. These values are unknown today. A measured recurring cost or access failure justifies a provider experiment. |
| **How much running detail is useful before a workout?** During A | Keep a dated purpose, effort, dose and adjustment cue at the top of the existing entry point. Use the weekly text export when useful. | Frequent missed follow-ups specifically because the Mac is inaccessible can reopen private phone access. The athlete previously declined watch export. Reconfirm that choice only if a new execution problem emerges. |
| **Which priority survives a disrupted week?** Before F | Start from the active block objective/ranked race, actual recovery and confirmed lifts. Ask which goal can give way only when they conflict. Reuse the current home-timezone convention for occasional travel. | A fixed race, a non-movable lift or an actual temporary availability window changes the feasible choice. Confirm cross-training mode and access before proposing a substitute. |
| **How detailed should performance feedback be?** Before G | Use a comparable observed result or training indicator alongside the target with its source/date. Leave uncertain ability unknown. | An upcoming race requires a pace decision that these observations cannot answer. Add an uncertainty range only with comparable history and a held-out error check. |
| **What constitutes recovery from a lost Mac?** Before maintenance | Keep backup/restore local and verifiable. Define whether a separate private backup location is already covered by the owner's practices. | If protecting against disk loss is required and no independent copy exists, choose a destination, confidentiality and retention policy, then restore-test it. A working local daily backup alone settles a different failure mode. |

## Candidates to leave outside the roadmap

| Candidate | Current disposition and evidence that could reopen it |
| --- | --- |
| Broad strength/hypertrophy or HYROX coach | Use Strong and confirmed running constraints. A separate athlete goal and scope decision after rehab would be needed for exercise programming, unit conventions and evidence work. |
| Private phone, wearable workouts or shared Google scheduling | Continue local use and existing text export. Identify a recurring missed action first. Google travel reads, Google publishing consent and Garmin workout delivery are distinct integrations. |
| Always-on AI, in-app chat, autonomous plan activation | Local calculation, accepted calendar and occasional reasoning fit the actual cadence. Test whether an existing handoff causes abandonment before funding another conversation surface. Keep the acceptance contract. |
| Body composition, gear tracking, calorie targets and broad nutrition logging | They do not currently explain a critical recurring running decision. A repeated fueling issue on long runs could justify a targeted question and evidence check. Shoe inventory can remain in an external tool. |
| Universal readiness/injury-risk score or a mandated weekly mileage percentage | Available observations have unequal reliability, timing and confounding. A small set of qualified facts can justify the immediate decision more clearly. |
| A generic lifestyle planner, central database or scheduling platform | No second consumer or integration requirement exists. Keep the running boundary documented and use a read-only projection if that changes. |
