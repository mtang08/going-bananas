# Running experience walkthrough

Reviewed 2026-11-24. These are representative paths through the checked-out app using the existing tests and current user guide. The [current-state inventory](current-state.md#verification) records which checks ran for this audit.

## Today and workout execution

1. Open Home. The mileage gauge and **Planned vs done** summarize the accepted week and its actuals. **Today's plan** and the week's session list let the athlete open an accepted prescription and see purpose, targets, repeated steps, guidance and any saved provisional badge. Setup and short-plan states prompt the athlete to populate or review the calendar. Home still presents independent panels when an individual query fails. [Home](../../../frontend/src/pages/Home.tsx), [Home tests](../../../frontend/tests/home.test.tsx), [Today browser case](../../../e2e/p0a.spec.ts)
2. Before a run, use the prescription's adjustment rules or record pain, fatigue, gait change, illness or context through **Record check-in** in the global header. A check-in can log context for the next review or produce a finding with a coach prompt. A coach recommendation runs in Codex, after the athlete starts it. [App header](../../../frontend/src/App.tsx), [check-in](../../../frontend/src/pages/CheckinModalV2.tsx), [exception guide](../../user-guide.md#exception-review)
3. After a run, wait for Garmin ingestion or use **Sync now** in real mode. The app shows job status and distinguishes partial data from successful completion. Treadmill intervals requiring pace confirmation create another user step. Matching compares same-day sessions and workout subjects, retaining ambiguous and cross-date candidates for review. A recording can remain unlinked until the athlete resolves it. [Sync card](../../../frontend/src/components/SyncCard.tsx), [sync API](../../../backend/app/api/sync.py), [matching](../../../backend/app/services/matching.py), [sync tests](../../../frontend/tests/sync-card.test.tsx)
4. Inspect the recorded run from its session or Activity. Prompted post-run feedback saves RPE, optionally a reason on the linked modified completion, then the check-in when needed. Those writes are sequential. The form keeps its progress for an in-place retry, and the tests exercise a failure after an earlier step succeeds. Delayed follow-up has a separate pain/gait form. Sessions without recordings can be self-reported from Calendar and count as completed while measured quantities remain unknown. [Check-in form](../../../frontend/src/pages/CheckinModalV2.tsx), [check-in tests](../../../frontend/tests/checkin.test.tsx), [manual outcome tests](../../../backend/tests/integration/test_manual_completion_refresh.py)

## Missed or changed run

- For an eligible session today or later, open the workout in Calendar and edit, move or delete it. The saved edit increments the calendar version and can stale a pending proposal. Calendar can display a historical version, and restore is available for eligible history with completion protections. [Calendar](../../../frontend/src/pages/Calendar.tsx), [calendar API](../../../backend/app/api/calendar.py), [protected undo case](../../../e2e/p0b.spec.ts)
- For an eligible past session, **Record outcome** offers **Skipped**, **Not recorded**, or **Link a run**. The run picker covers the surrounding day on each side. Linking a run from a different date records a confirmed move on the server. Home's reminder says to mark the session moved, while the past-session dialog expresses that action as linking a run. The direct **Move** control edits today's or a future prescription. [Home](../../../frontend/src/pages/Home.tsx), [Calendar outcome dialog](../../../frontend/src/pages/Calendar.tsx), [completion rules](../../../backend/app/services/calendar.py)
- For a linked run that differed from the plan, use the execution comparison and available feedback. Mileage, completion status and reported reasons are separate evidence. The weekly digest can expose missed, unrecorded, changed and unplanned work without quietly rescheduling a missed run. A material disruption can lead to a separate in-chat exception proposal and an app decision. [Activity](../../../frontend/src/pages/Activity.tsx), [weekly digest](../../../backend/app/services/weekly_digest.py), [exception browser cases](../../../e2e/p1-exceptions.spec.ts)

## Sunday review and proposal acceptance

1. Start the review in Codex. The repo-local skill routes from the active block, accepted calendar, review timing, actuals, feedback and verified evidence. The normal cadence is athlete-initiated Sunday review, with extra reviews for meaningful changes. The digest gives the app and coach shared weekly figures. [Coach skill](../../../.codex/skills/going-bananas-coach/SKILL.md), [Sunday guide](../../user-guide.md#sunday-review), [digest browser cases](../../../e2e/p2-weekly-digest.spec.ts)
2. Discuss the plan and any counterproposal in chat. When the athlete agrees or asks to publish, the coach saves the pending proposal or revises its existing link. Home shows it in **Needs attention**. In-app proposal editing by the athlete is a backlog item. [Proposal guide](../../user-guide.md#review-and-revise-a-proposal), [counterproposal backlog](../../backlog.md#idea-007--athlete-counterproposals-with-coach-review)
3. In Proposal Review, see why the plan changed and compare the dates and workouts. Select the desired session changes and any relevant block or anchor changes, then apply or reject. The decision carries the calendar head and the reviewed revision. Stale evidence or a newer revision blocks acceptance, and a reload clears selections tied to an old revision. An identical request can retry a lost response. [Proposal review](../../../frontend/src/pages/ProposalReview.tsx), [frontend tests](../../../frontend/tests/proposals.test.tsx), [proposal API tests](../../../backend/tests/integration/test_proposals.py)
4. Check the resulting accepted plan on Home or Calendar. The checked-out browser journey exercises partial acceptance and checks that later snapshot inputs carry outcomes. It uses a synthetic proposal and therefore leaves open whether a freshly reasoned review consistently produces useful workouts or needs rework. [Weekly browser journey](../../../e2e/p0b.spec.ts)

## Interrupted schedule, goals and calendar changes

- Open Settings to sync an existing read-only Google connection, review detected trips or create a manual one. Set travel dates, destination timezone, access and availability as known. Calendar displays badges and the coach can account for trip constraints when drafting revisions. The ordinary app calendar stays on the configured home dates, so destination dates can affect how an activity lands. Temporary non-travel constraints can be reported in chat or check-ins. Dedicated disruption kinds and daily time windows remain backlog ideas. [Travel guide](../../user-guide.md#travel-from-google-calendar), [trip UI tests](../../../frontend/tests/travel.test.tsx), [travel refresh test](../../../backend/tests/integration/test_travel_refresh.py), [backlog](../../backlog.md)
- Use Settings for stated goals and ranked events. Goal-race ranking feeds the block target and race timeline. Reordering, canceling or passing the target can prompt a block review. The athlete can inspect the benchmark and choose an activity match on the Block page. Changes to the accepted workouts require a separate proposal decision or direct calendar edit. [Goals](../../../frontend/src/pages/settings/Goals.tsx), [events](../../../frontend/src/pages/settings/Events.tsx), [block page](../../../frontend/src/pages/Block.tsx), [planning tests](../../../backend/tests/integration/test_planning_api.py)
- The weekly Calendar text download is the existing portable workout format. The trip workflow consumes provider calendar information. Scheduling accepted workouts into time slots and writing them back to Google remain open. [Weekly export](../../../frontend/src/components/weeklyWorkoutExport.ts), [Google scheduling backlog](../../backlog.md#idea-008--schedule-and-share-training-plans-in-google-calendar)

## Remaining evidence

The UI walkthrough used fixture-driven interactions. Saved aggregates also confirm that real completions and RPE reached two subsequent accepted reviews. [Observed use](data.md#what-the-saved-reviews-demonstrate) A full cycle from a freshly reasoned coach draft through app acceptance, provider recording, ambiguous match resolution, feedback, and the following review remains unobserved here. The largest practical unknowns are whether the athlete can find these actions at the moment they matter, how often matching or feedback needs manual recovery, and whether the next review uses the recorded context to propose a credible adjustment. [Verification record](current-state.md#verification), [coaching evaluation backlog](../../backlog.md#idea-013--evaluations-that-catch-coaching-quality-regressions)

## Highest-friction moments to test with the athlete

| Moment | Friction or uncertainty | Useful change and observation |
| --- | --- | --- |
| Leaving for today's run | Sync status, weekly mileage and digest precede the dated prescription in Home. The guide, calendar, proposal and chat can all contain reasons at different depths. | Put the accepted session, effort and adjust-if instruction first. Make weekly diagnostics secondary. Time how long it takes to answer “what do I do now?” on an ordinary day and on a day with a caution. |
| Seeing activity and recovery | Trends and activity detail can explain individual measures. The athlete still has to relate them to the intended stimulus. An incomplete input may require a different action from an unusual workout. | Link the specific question to the recorded session or recovery window and its quality flags. Test with an easy day with partial HR coverage and a key workout with incomplete reps. |
| Finishing or revisiting a workout | The runner may report in Garmin, record RPE in Going Bananas, open Activity for execution, use Calendar to resolve a move, and see a later Home prompt. An unobserved answer in this sample could reflect access, timing or preference. | Reuse valid watch RPE, name the unresolved action, offer a direct route from the workout, and keep delayed reporting selective. Observe one completed run before attributing friction to the lack of a phone client. |
| Conducting the next Sunday review | The week digest, rolling horizon, block screen and conversation each answer part of the retrospective. A draft can expire as new evidence arrives. | Start with the last intended change, its known result, open questions and one proposed priority for days 1–7. Keep days 8–14 detailed enough to anticipate conflicts, flag their provisional status and link back to the accepted revision. |
| Assessing a season | Goals/settings, block indicators, activity history and benchmark results live on different surfaces. A base block may have no result time. | Answer “is my current approach working?” with the active objective, its chosen indicator, reference period, response coverage and next check. Use a race result only when applicable. |

These are design hypotheses. A task passes when the athlete can give the correct answer and act from the normal entry point after a fresh start. Observe elapsed time, wrong turns and repeated data entry before funding a dashboard redesign.
