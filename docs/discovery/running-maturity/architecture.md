# Running planning boundaries

Repository audit dated 2026-11-24. The current path below was traced through the implementation and representative tests. The planner boundary is a design option assessed from those contracts.

## Current loop

1. Garmin, Strong and Google Calendar enter through separate local adapters. Canonical records retain source identity and coverage. Source writes share a transaction with the scoped work they trigger, including matching, metric refresh and prompts. The read layer supplies accepted session state and eligible actuals. [App architecture](../../architecture.md), [derived refresh](../../../backend-go/internal/metrics/refresh), [shared calendar reads](../../../backend-go/internal/calendarhttp/reads.go)
2. The athlete starts a review in Codex. The repo-local helper requests an operation-scoped snapshot, which includes the accepted calendar head and the relevant parts of the block, athlete report, actuals, metrics, race targets, strength, and travel. It selects verified research and keeps raw provider data outside the coaching payload. The local app calculates metrics and runs its exception detector deterministically. [Helper](../../../.codex/skills/going-bananas-coach/scripts/coach_app.py), [snapshot build](../../../backend-go/internal/coaching/snapshots/build.go), [payload](../../../backend-go/internal/coaching/snapshots), [decision facts](../../../backend-go/internal/coaching/evidence)
3. Once the athlete agrees or asks to save, the helper submits or revises a `coach_proposal.v2` document through the CLI. The service checks context, evidence, dates, structure, protected history and applicable safety rules, then stores a pending draft. A revised draft keeps the same link. The app reads proposal revision and freshness independently of its accepted session state. [CLI](../../../backend-go/internal/coachcli), [proposal schema](../../../backend-go/internal/coaching/drafts/parse.go), [submission and revisions](../../../backend-go/internal/coaching/drafts/store.go), [validation](../../../backend-go/internal/coaching/drafts/validate.go)
4. The athlete reviews the proposed changes in-app. The decision handler rechecks snapshot freshness, reviewed revision and the selected subset, then writes the accepted calendar version and related decisions atomically. Completed or locked records have explicit protection. Subsequent matching, check-ins and results give the next review an outcome to assess. [Accepting a proposal](../../../backend-go/internal/coaching/drafts/decision.go), [calendar](../../../backend-go/internal/calendar), [matching](../../../backend-go/internal/matching), [release verification](../../release-checklist.md)

A multiweek build outline can describe phases leading to the race while the calendar carries bounded dated sessions. Rolling, block and race-change proposals can start today and extend to the relevant block review date, clamped to 13–42 days from today. The current guide treats days 1–7 as committed and later accepted sessions as provisional. A pending proposal sits outside the accepted calendar and its weekly distance projection. [Scopes](../../../backend-go/internal/coaching/drafts/parse.go), [target and outline checks](../../../backend-go/internal/coaching/drafts/validate.go), [README](../../../README.md), [accepted-head projection](../../../backend-go/internal/weeklyprojection)

## The smallest future scheduling contract

Consider a planner that wants to find a time for Thursday’s run. Its questions are “which dated session is accepted, how long might it take, what placement is flexible, and has it changed since my last read?” A useful read projection would expose a stable running session ID, revision/calendar head, committed or provisional status within the accepted plan, home-zone date, optional duration/range and time window, and display label. Separate read-only views could supply an actual with completion confidence, a dated availability constraint, and a pending recommendation with expiry/base revision. The downstream consumer needs the scheduling consequence of a restriction (for example, unavailable or review before moving) without receiving clinical details, raw sensor traces, RPE history, or private calendar titles by default.

If an external planner later wants to move that run, it can submit the desired date/window with the session ID and observed revision to a running-specific adapter. The running domain checks sequencing, recovery, restrictions and conflicts, explains the consequence and returns a candidate for athlete review. An obsolete revision requires a fresh read. On acceptance a consumer can observe the new version. Implement this interaction only if a consumer needs it.

## Decisions for this project

**Justified during running work.** Reuse the current read services for UI, coach and any later local projection. Keep stable session identity separate from revision, preserve provenance and quality in derived measures, and include changed decision-relevant metric configuration in freshness. Verify the accepted calendar is still usable if Codex, Google or Garmin is offline. These changes pay their way for the runner today. The first two are existing design properties to preserve. [Read models](../../../backend-go/internal/calendarhttp) · [Freshness vector](../../../backend-go/internal/coaching/evidence) · [Known configuration gap](../../backlog.md#deferred-follow-ups-from-shipped-features)

**Wait for a named consumer.** A versioned export, time-slot negotiation, change feed, Google publishing, authentication for another app and conflict semantics need an actual consumer and scheduling requirement. Use a bounded pull first when that day comes. The current weekly text download already works for a human. Sharing a database, repository or deployment, a universal activity schema, an event bus and cross-domain planning logic have no running acceptance case. The running app should start, store history, explain training and accept a local plan on its own. [Current local operation](../../operations.md)
